# 🔥 Отчет по Дню 1: Rules

**Проект:** QA Scenario Manager (Desktop-first Kotlin / Compose Multiplatform)
**Цель:** Оценка влияния системного файла `CLAUDE.md` на качество генерируемого кода при выполнении zero-shot промптов.

---

## 1. Файл правил (CLAUDE.md)
Перед началом эксперимента был сформирован базовый файл правил для агента.

**Что вошло в правила:**
* **Стек и архитектура:** Kotlin, Compose Desktop, Coroutines, StateFlow, Unidirectional Data Flow (UDF).
* **Паттерны:** Один экран = один State объект, State hoisting (никакой бизнес-логики в `@Composable`).
* **Антипаттерны (что запрещено):** Смешивание UI и Data слоев.
* **Шаблоны файлов:** Приведены примеры MVI-контрактов (`State`, `Event`) и чистых репозиториев.

---

## 2. Эксперимент (Итерация 1)
**Задача:** Написать сервис экспорта и импорта сценариев в JSON файл.
**Промпт (Zero-shot, без уточнений):**
> "Implement the JSON export and import feature for scenarios. Add the necessary UI components (buttons for import/export), state management, and data persistence logic to save and load scenarios from a locally selected JSON file. Give an example on how to test it."

**Результат 1-й генерации:**
Ассистент выдал рабочий (компилируемый) код, но с грубейшими архитектурными ошибками:
1. **Нарушение слоев (SoC):** В Data-слое был захардкожен `javax.swing.JFileChooser`. Сервис сам пытался открывать UI-диалог.
2. **Блокирующий I/O:** Использовались синхронные `file.readText()` и `file.writeText()`, что заморозило бы UI в Compose Desktop.
3. **Обработка ошибок:** Обычный `try/catch` с возвратом кастомных стейтов, но без интеграции с корутинами.

---

## 3. Усиление правил (Доработка v2)
Проанализировав провал, файл `CLAUDE.md` был обновлен. Вместо простых указаний были добавлены абстрактные принципы подкрепленные конкретными примерами "Как надо" и "Как запрещено":

**Добавленный блок в CLAUDE.md:**
* **Strict Separation of Concerns (SoC):** Явный запрет на использование UI-компонентов (Swing, AWT, Compose) внутри Services/Repositories. Data-слой принимает только абстрактные `Path` или `File`. Приведен пример антипаттерна с `JFileChooser`.
* **Non-blocking Main Thread:** Явное требование делать файловый I/O через `suspend` функции с использованием `withContext(Dispatchers.IO)`. Приведен пример использования `runCatching` с возвратом `Result<T>`.

## 4. Повторный запуск (Итерация 2)
Тот же самый ноль-шот промпт был отправлен в новом чате с обновленным `CLAUDE.md`.

**Результат 2-й генерации (Дифф):**
* ✅ **Separation of Concerns:** Отработало идеально! Ассистент полностью удалил UI (`JFileChooser`), внедрил `ScenarioRepository` через конструктор и стал принимать `java.nio.file.Path`.
* ✅ **Нативные библиотеки:** Использован строго `kotlinx.serialization` с правильными настройками (`ignoreUnknownKeys = true`).
* 🎁 **Неожиданный бонус:** Во второй генерации Claude **самостоятельно сгенерировал Unit-тест** на класс `ScenarioJsonService`, хотя об этом не просили. Это частый эффект качественного контекста: когда код "чистый" и легко тестируется (dependency injection), LLM склонна дописывать тесты по своей инициативе.
* ❌ **Частичная потеря контекста:** Несмотря на правила, ассистент "забыл" сделать методы `suspend` и не использовал `Dispatchers.IO` (оставил блокирующий I/O).

---

## 5. Выводы (Что больше всего повлияло на качество)

1. **Абстракции + Примеры антипаттернов:** Просто написать "Не используй UI в Data слое" работает хуже, чем дать абстрактное правило (SoC) и показать конкретный антипаттерн с `JFileChooser`. Это дало 100% эффект исправления архитектуры.
2. **Чистота порождает чистоту:** Как только код стал соответствовать принципам Dependency Injection (передача `Path` и `Repository`), агент автоматически сгенерировал Unit-тест. Хорошая архитектура провоцирует LLM на написание лучших сопутствующих артефактов.
